# What's Working

Threads isn't dead. Most of your posts are. This workflow reads every post you published this year, labels each one against **your own median views** (dead, stuck or alive), answers "is Threads dead for me?" month by month, names what the dead posts share and the one kind of post Threads still pushes hardest, then asks Threadify to write three new posts in that pattern, with editable review and optional Auto Plugs, and schedules them only after one "yes". It works the same in Claude Code, Codex and ChatGPT.

Follow [Threadify-001: setup and first-loop video](references/threadify-001.md) before the first connected call. A connection never authorizes scheduling. Only the owner's "yes" to the exact approval packet does.

## Rules

- Follow [demo feedback rules](references/demo-feedback-rules.md) for the whole run. If `~/.threadify/owner-overlay.md` exists, read it too and follow it; it is private, so never quote it into posts, files you publish or receipts.
- Every number comes from the tools or the script. Missing data stays unknown: say "unknown", never 0. Describe what happened, never what will happen: no post or pattern "will" go viral.
- Say "this year" only when the read starts on 1 January. Otherwise say the real window: "read N posts, <first date> to <last date>".
- Threadify writes every post and every plug with `generate_content`. Preserve generated wording by default; the agent edits only when the owner explicitly asks. Record the request and original copy. Never use `edit_draft`.
- Without an editing request, the only permitted change is lowercasing, keeping proper nouns, and only when the owner asks for it. Prove it for every post and plug with `scripts/casing-guard.mjs` (Node 18+, JSON on stdin): `lower(original) == lower(final)` must be true and the result PASS. If the guard fails, show the original unchanged.
- After generation, open three editable post blocks using [editable review](references/editable-review.md). Prefer supported native editing with a real Done editing event; otherwise run the bundled local editor. Keep the report open. Autosave is not completion, and Done editing is not scheduling approval. Preserve originals and record exact owner revisions.
- Auto Plugs are optional and off by default. An explicit request to skip them overrides the plug steps; never call offer or plug generation tools for a post-only run.
- Never publish now. Never schedule without the owner's "yes" to the exact packet. Never move or overwrite a post already on the calendar.
- Never print credentials, tokens, account ids, other people's handles from replies, or customer details. Show the owner's own posts and numbers; they are the point.

## Steps

1. **Connect.** Call `get_connection_defaults`. Confirm the account by saying only the @handle and timezone, for example "@handle · Australia/Perth". Note `link_tracking` and whether Auto Plug is available; leave it off unless the owner opts in. Say in one line what the owner gets: "I'll check every post you published this year against your own median, show you what Threads is killing and the one kind it still pushes, then Threadify writes 3 of those for you."
2. **Read the year.** Call `search_posts` with `query: "*"`, `from` / `to` set to one calendar month at a time from 1 January to today (`to` is exclusive: use the first day of the next month, and tomorrow for the current month, or the last day of every month goes missing), `sort_by: "recent"` and a `limit` above that month's `total_matched`; if a month returns fewer rows than `total_matched`, split it into halves and read again. Keep every page, and check that the months' row counts add up to the total before you diagnose. (`read_post_performance` with a long window can fail with `artifact-write-failed`; use it only for a window it returns in full.) If the account's history doesn't reach 1 January, keep what it returns and say the real window. Save the raw pages locally (never in a public repo).
3. **Diagnose.** Pipe `{"performance": <every search_posts page>, "from": "<YYYY>-01-01", "handle": "@handle"}` into `node scripts/whats-working.mjs --html whats-working.html`. Say the coverage line first ("Read N posts, date to date. Counted M; K too new to judge; U with unknown views."), then the median, the best post and its multiple, and `never_broke_out_percent`. Labels are relative to the median: **dead** under 1x, **stuck** 1x to under 3x, **alive** 3x or more; posts under 3 days old are left out because they are still collecting views. Then answer "is Threads dead for you?" from `monthly`: compare the first and last full months' median views and alive share, in numbers, with no verdict the numbers don't show.
4. **Name the patterns.** Read the posts (top 30 by views, the 30 lowest, and every alive post) and give each counted post one short pattern label that joins its hook and format, for example "news reaction", "i got AI to do a huge task", "hot take", "how-to list", "personal story", "question", "promo". Use the owner's own words for topics. Use 6-10 labels in total so groups are big enough. Re-run the script with `"tags": {"<post_id>": {"pattern": "<label>"}}`. Patterns with fewer than 5 posts are marked `small_sample` and are not ranked; say so if one looks big.
5. **Show what's working.** Open the report page and keep it on screen: serve its folder on this computer only (for example `python3 -m http.server 8047 --bind 127.0.0.1 --directory <report folder>` in the background) and open `http://127.0.0.1:8047/whats-working.html` in the browser, because some hosts' browsers refuse `file://` pages. Stop the server when the run ends. In chat, keep it short and phone-readable (no wide tables):
   - **What Threads killed:** up to 3 `most_dead` patterns, each with its median multiple and one real post (first line + views).
   - **What it still pushes:** `most_alive`, ending on **#1** (`number_one`): its median multiple, alive share and its 3 real example posts.
   - One line: what the #1 posts share that the dead ones don't (first line, subject, format), tied to the examples. Describe, don't predict.
6. **Threadify writes 3 in the #1 pattern.** Make one `generate_content` call per post with `strict_facts: true`, `inputText` describing the #1 pattern as a shape (never a past post's copy to paste) plus a fresh subject from the owner's own recent topics, and `selectedModel` from [generation models](references/generation-models.json) (Claude Opus 5.5 when the plan allows it, Gemini as fallback; record the requested and reported model). Ask for a concise, concrete research hook that names the actual analysis task and its benefit to the reader, then a few short factual beats or a compact findings list, and one direct practical or emotional closing point in the owner's voice. Prefer a useful takeaway over setup, coverage bookkeeping, repeated explanation or tidy caveat-heavy endings. Only name the model or tool that actually performed the research; the drafting model did not necessarily read the full source archive. Call a median a median, never an average. Preserve opinion as opinion and never turn past views into a claim that a post was destined to fail. Do not prescribe profanity, capitalization or personal facts independently of the owner's Brain and request. These are general writing patterns, not permission to copy an owner's prior body. Give numbers as whole numbers, and keep the analysis caveats (association, sample size) in the report, not in the post. No offer and no link in the post itself. Keep Threadify's exact text and `draft_id`. If the owner wants lowercase, run `casing-guard.mjs lowercase` with the proper nouns to keep, then `check` on every post; show "guard: lower(original) == lower(final) PASS" per post.
7. **Owner edits and optional Auto Plugs.** Open the editable review as described in [editable review](references/editable-review.md), with one block per post and a **Done editing** button. The local fallback also has an **Include Auto Plugs** checkbox, off by default. Honor any earlier explicit choice; the owner can change it during review. Wait for the real completion event or the local editor command to finish, then read its saved receipt. Compare each original, initial casing-approved copy and owner-final copy; keep the exact edited bytes, set mode to `owner-requested edit` when wording changed, and summarize wording/format lessons separately from fact changes. Never call an owner rewrite casing PASS. Save task-specific learning notes locally; do not publish their bodies or promote one revision into an unrequested global voice rule.

   If Auto Plugs are off, skip `list_offers`, plug generation, destination checks and plug validation, and set `packet.auto_plugs: false`. If the owner opts in, set `packet.auto_plugs: true` and generate one Auto Plug each: Call `list_offers` and let the owner pick one offer if more than one fits. For each post, make one more `generate_content` call with that `offer_id`, asking for a one-post plug reply that continues that exact post. Run the guard on each plug the same way. Promote the selected offer, and claim only what its destination provides. The plug's link is the offer's saved destination; Threadify links on Threads are auto-tracked, so add no UTM tags. If `link_tracking` is off or unknown, say clicks may not be measured. If the plan has no Auto Plug, say so and ask whether to schedule without plugs or stop.
8. **Review and pick 3 slots.** Follow [review and editing](references/review.md) and run `node scripts/review-packet.mjs < review.json` as described there, including the Done editing receipt when using the local editor. Post-only packets use `auto_plugs: false` with no plugs or destinations; do not bypass the checker or attest unreviewed facts as verified. Call `best_time_to_post` (owner's timezone) and `list_scheduled_posts`; a truncated response is not an empty calendar. Pick one slot on each of the next three days at the best measured time with no scheduled post within 90 minutes and at least 60 minutes from now. Call `validate_post` on every final post and on plugs only when enabled; if one fails, say why and ask Threadify once for a replacement through steps 6-7.
9. **One approval packet.** Send one message:

```text
What's Working · @handle · <timezone>
#1 pattern: <label> · <median multiple>x your median
1) <weekday date, local time> · <unchanged | casing guard PASS | owner-requested edit>
<exact final post text>
Auto Plugs: <off | on>
<only when on: Auto Plug (15 min after): exact plug text; Destination: exact offer destination>
2) ...
3) ...
Action: schedule these 3 posts exactly as shown with Auto Plugs <off | on as shown>. Nothing publishes now.
Reply "yes" to schedule all 3, or "no" to schedule nothing.
```

   Schedule only on an explicit "yes". Any change to text, plug, destination, account or time needs a new packet and a new "yes". On "yes", re-check `list_scheduled_posts`, then call `schedule_post` three times with a stable `idempotency_key` per post (account, slot, final post and plug hashes) and, only when enabled, `auto_plug: {content: <exact plug text>, trigger: "time", delay_minutes: 15}`. For a post-only packet omit `auto_plug` entirely. Unchanged text: pass `draft_id` and `content_type`. Lowercased or owner-edited text: pass the exact final `text` without `draft_id`, because Threadify schedules a draft's stored text when given a `draft_id`. Omit `platforms` and `auto_repost`. Read back each one with `get_schedule_status`: text, local time and the enabled plug echo or verified disabled/null plug state must match the packet; a failed or cancelled record is a mismatch. If an outcome is unclear, read back before retrying, and retry only that post with the same key. On "no", schedule nothing; originals stay as Threadify drafts.
10. **7-day check.** Offer to re-run What's Working 7 days after the last of the 3 posts goes out, to see where they landed against the median. If the host supports a reminder or scheduled run, offer to create one and create it only after the owner agrees. Otherwise give a dated note: "Run What's Working on <date> to see where these 3 landed."

## When something is missing

If the owner asks to record workflow feedback, retain a local change-request note and remind them at completion; do not automatically publish their copy, update an installed workflow or create a reminder without authority.

Without a Threadify connection or generation access, stop and say exactly what is missing and the manual next step. Never write posts yourself instead. A scheduled post is not a published post.

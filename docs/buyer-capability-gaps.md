# Buyer workflow capability gaps

The buyer workflows prepare useful work locally from an offer and conversations you supply. Connect a provider only for a step that benefits from current account data or a supported delivery surface.

| Need | Current path | Proof limit | Manual fallback |
|---|---|---|---|
| Offer context | Offer Builder local interview and handoff | A local offer is owner-confirmed context, not customer proof | Write the offer, buyer, deliverable and limits in the review artifact |
| Conversation source | Supplied text, file or host-inspected Threads conversation | The local module records minimal evidence and cannot prove the source is still current | Reopen the source, record its URL or stable reference, observed time and factual note |
| Lead classification | Relevant interest in help or the offer, checked against the confirmed offer | A public question, like, follow or profile label does not make a lead | Mark the item as a conversation signal and ask the missing discovery question |
| Public Threads reply | Qualified Buyer Research may inspect and stage one useful offer-free reply | QBR stops before Send; a filled composer is not a sent reply | Copy the approved text into the verified branch and let the owner send it |
| DM, email or call step | Host tool only after current capability, recipient interest, channel permission and exact owner approval are all shown | The public package has no generic cross-provider send/readback contract | Show exact recipient, destination and text; owner completes the action and records the result |
| Commitment tracking | Local explicit promise, owner and due date | Silence and vague intent do not create or close a commitment | Review the open list and record `fulfilled`, `declined`, `withdrawn` or `uncertain` |
| Review reminder | Host-native reminder after explicit opt-in | `reminder` reports a candidate and creates nothing; reminders never send | Put the review time in the owner's chosen calendar or task app |
| Buyer question content | Local deidentified evidence and draft packet | One question is one signal; repeated evidence needs distinct sources | Remove identifying detail, label the evidence count and prepare a local draft |
| Weekly outcomes | Local seven-day report from receipts and owner updates | Likes are not sales; `owner_reported` and `provider_observed` evidence stay separate, and only authoritative readback supports a verified claim | Add the missing source or leave the outcome unknown |

## Client proof status

The source package and adapters can be checked structurally. Codex and Claude Code passed native discovery and a synthetic first run of Your Next Moves; the five-workflow engine sequence passed separately. See [0.8.0 acceptance](buyer-experience-acceptance.md). Cursor, Gemini CLI, OpenClaw, Hermes and generic MCP guidance is structural until each client completes its own native walkthrough.

The local state engine currently targets macOS and Linux. A Windows installer result confirms installation only. It does not confirm local state creation, locking, revision recovery or end-to-end conversation use.

## Current MCP use

Use only tools exposed by the current connected MCP and named by the selected workflow. Start with account and capability readback when connected. Missing tools stay missing; do not translate a similar provider response into Threadify proof.

Keep unsupported steps in a local review artifact. Before any external action, re-open the source, show the exact destination and content, obtain exact approval, persist the pending attempt, then reconcile the real result. Unknown delivery blocks replay.
